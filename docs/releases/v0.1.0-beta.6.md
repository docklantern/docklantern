# DockLantern v0.1.0-beta.6 — Release notes

**Preparation record (2026-11-07):** beta.6 has passed the described disposable-VPS host-executor and locally built monitoring-image acceptance tests. **G7 publication was not yet authorized at this checkpoint.** This text is prepared for a future independently approved version tag and is not an authorization to tag, publish or deploy.

## What's new

- **Separate on-demand host executor.** The root-owned `docklantern-executor apply <proposal-id>` handles one approved Compose service update, after protected registration, a short-lived untrusted proposal, independently verified immutable public image evidence and exact host-local interactive `APPLY` confirmation.
- **Scoped immutable Compose replacement.** Project locking, trusted source/registration requalification, fixed Docker/Compose runtime, journaled phase intents, target-only replacement, actual container-image inspection and sibling-invariance checks. A verified commit is recorded only after post-update checks.
- **Monitoring GUI remains read-only for deployment.** Services and images distinguish registry observations from deployment eligibility; no web endpoint can approve or execute a Compose update.
- **Deployment Activity.** An authenticated read-only view can show bounded, sanitized executor receipts only if a separately approved read-only mount is available. A missing/stale receipt reports **unknown/unavailable**, not success.
- **Independent security evidence.** CI checks the monitoring image and proxy and scans the separately built executor binary. The executor is neither bundled into nor invokable by the monitoring container.

## Important beta limitations

- **Narrow image-update scope:** only an independently registered, single public Docker Hub `linux/amd64` prebuilt image and supported Compose structure on the pinned Engine 29.8.1 / API 1.56 / Compose 5.5.1 runtime have witnessed host-executor acceptance.
- **Explicit local approval required:** no GUI-to-executor connection, unattended or automatic deployment, batch/multi-service update, private-registry deployment, self-update or critical-infrastructure update is supported by this first path.
- **No `recover` or automatic rollback:** uncertain/interrupted operations block new work and require a new, separately approved manual inspection and repair plan. Image rollback does not reverse application data, volume or database changes.
- **Compose files are not rewritten by the executor:** desired image generations are stored in protected executor SQLite; the selected image override is supplied to Compose through a private stdin stream. A later unmanaged Compose operation using the old YAML may revert the deployed image.
- **Running-only is weaker than healthy:** the G5 fixture had no HEALTHCHECK and its reduced readiness standard was expressly approved. The tested monitoring container itself had a passing Docker healthcheck.
- **Registry digest observations are not authorization:** different watched digest/tag hints do not independently prove a safe release or authorize an update.
- **Activity receipts require a separate read-only mount:** successful host journal status is not visible in Activity on a monitor without that mount, and the GUI must remain in an unknown state. No executor journal or registration should be mounted into the monitor.
- **Beta.5 monitoring behavior is preserved:** watched tags, Check Now, registry observations and monitored services remain monitoring-only. Beta.5 and beta.6 monitoring use SQLite schema version 5 in this tested code; preserve a compatible application backup for rollback.
- **Production recovery evidence is incomplete:** no off-host backup/restore, executor protected-state restore drill, positive Activity receipt integration or live interrupted-operation recovery was accepted. Do not describe this disposable-host test as production certification.
