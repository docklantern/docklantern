# DockLantern v0.1.0-beta.6 — release candidate notes (DRAFT / NOT RELEASED)

**Release status: NO-GO.** This document prepares operator review. It does not authorize tagging, package publication, installation or Docker mutations.

## What's new

- **Separately operated host executor:** a root-only, on-demand `docklantern-executor apply <proposal-id>` command can attempt a single pre-approved Compose service image replacement after protected registration, independently qualified public immutable image digest and interactive host-local terminal confirmation.
- **Narrowed effect scope:** targeted Docker/Compose operation, project lock, source stability and Compose image-only comparison, journaled intent before effects, selected-service image inspection and sibling-invariance verification.
- **Read-only GUI deployment review:** image and service views distinguish watched registry references, Docker-observed image evidence, unknown host eligibility and external authorization; the monitoring GUI cannot execute, approve or recover an update.
- **Deployment Activity:** sanitized executor-journal receipts if an independently approved read-only mirror is present. A missing or stale receipt means current deployment state is unknown.
- **Security checks:** executor binary vulnerability audit and short-lived CI artifact with SHA-256/source evidence, separate from security-scanned monitoring/proxy images. CI's successful scans do not establish host acceptance.

## Important beta limitations

- The new executor applies only to **one approved public Docker Hub linux/amd64 prebuilt service** on a pinned local Engine 29.8.1/API 1.56/Compose v5.5.1 environment. Exact support on the VPS needs witnessed validation.
- **No GUI-to-executor connection**, unattended updates, automatic deployment, multiple-service updates, private registry deployment, self-update or critical infrastructure target.
- **No `recover` or automatic rollback**. Failed/uncertain operations block further apply and demand separately authorized inspection/repair. Image replacement cannot undo data migrations, volumes or application-side effects.
- User Compose files are not edited; the committed desired image is recorded in executor SQLite, so future unmanaged `docker compose up` using original YAML may replace the new image with the old reference.
- Observing a different registry digest does not establish a newer, trustworthy or safe software release. No-HEALTHCHECK running-only verification is weaker than healthy application readiness.
- The protected proposal publisher is intentionally not wired to the GUI. Host-local validation and approval remain required.
- The existing beta.5 watch overrides, Check Now, registry evidence and monitored services retain their monitoring-only behavior.
- The historical beta.5 SQLite schema requires a compatible application backup for any image rollback; switching an image tag alone is not a database rollback.
