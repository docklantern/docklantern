# PR #21 — Beta release candidate checklist (no publish)

The proposed first monitoring-only beta tag is `v0.1.0-beta.1`. This PR does **not** create that tag, push a GHCR image, or deploy DockLantern.

## Immutable container inputs

The Dockerfile builder and Alpine runtime stages use Docker Hub registry-verified OCI manifest-list digests, recorded in `build/base-images.lock`. The optional privileged socket proxy is pinned separately in `build/proxy-base.lock` and rebuilt with Alpine security updates. The monitoring image no longer ships Docker CLI, Compose or Buildx binaries. The Go build stage uses the Go 1.26 Alpine release line. CI verifies both Dockerfile references exactly match the approved lockfile.

Review digest updates as code changes. A tag alone is insufficient to guarantee a stable release; each deployed image should ultimately be referenced by the immutable digest generated by the tag-release workflow. Upstream base images, OS packages, Go dependencies, and the read-only Docker socket proxy still require periodic vulnerability review and deliberate upgrades. `apk add` resolves repository packages at build time, so the full image is not guaranteed bit-for-bit reproducible despite pinned base manifests.

## Required beta review gates

1. **Merge reviewed PR #21 and verify all CI jobs pass**, including Go unit/race/vet, Docker discovery proxy, and the complete monitoring flow.
2. Require all three jobs in `.github/workflows/security-audit.yml`: reachable Go vulnerabilities, fixable HIGH/CRITICAL vulnerabilities in the built monitoring image, and the optional Docker socket proxy. The tag release workflow now depends on this reusable audit. Review **unfixed** Trivy findings separately and document remediation or explicit beta blockers in `docs/security/beta-audit.md`. Automated scanning does not replace a manual security review.
3. Verify bind-mounted Compose secret ownership with `cap_drop: [ALL]`: on rootful Docker, the admin password and webhook HMAC key should be owned by root with mode `0600`. Check rootless/user namespace mappings separately; never chmod secrets world-readable.
4. Review unauthenticated `/healthz` and `/readyz` exposure, single-admin Basic-auth access, TLS trusted-origin settings, restricted Docker network membership, and secrets mounted from files.
5. Confirm update execution is **not wired into the monitoring binary** and the deployed stack mounts no Docker socket unless the opt-in proxy overlay is explicitly approved.
6. Test the disposable installation script using a clean CI runner. Verify readiness, monitoring-only registration, SQLite persistence across restart, online `VACUUM INTO` backup, and offline restore.
7. Inspect `.github/workflows/release.yml` to ensure publishing is triggered only by an explicitly pushed, reviewed semver tag. Restrict who can create release tags, using protected tag rules if available.
8. Only after approval: tag the reviewed main-branch commit as `v0.1.0-beta.1`, observe the test and signed provenance build, note the resulting image digest, and install it on an **isolated disposable** VPS or lab host.
9. Evaluate a realistic monitoring scenario against private GHCR and Docker Hub images, registry rate limits, event/webhook failures, database recovery, and operator documentation. Document any beta blockers before public availability.

## Disposable local validation

Run **only on an empty development host whose Docker daemon can be used for temporary containers and volumes**:

```sh
DOCKLANTERN_INTEGRATION_TEST=1 bash tests/integration/run-beta-install.sh
```

The script refuses to run without the explicit flag, builds the local image from source, launches a separate private Docker Compose project, never publishes ports or mounts the Docker daemon socket, writes only temporary registration/secret fixtures, backs up and restores SQLite in its disposable volume, and removes containers, volumes, images, and temporary files on exit.

This test is not a public Traefik deployment test. The existing package security integration checks trusted Host/HTTPS forwarding and credentials. Do not point any of these tests at production.

## Recovery / release rollback

- Keep a restorable off-host SQLite snapshot before replacing any deployed candidate.
- Use the immutable digest of the previously verified image to roll back.
- Stop all processes accessing the SQLite database before restoring. Move old `-wal` and `-shm` alongside the database; never attach them to a restored backup.
- After restore, validate `/readyz`, project registrations, monitoring policies, and pending notification outbox.
- Do not assume downgrading the binary is compatible with any newer migrations unless explicitly validated.

## Known limitations

No production-ready SSO, multi-user authorization, update execution, coordinated multi-instance SQLite writers, automatic tag-version ordering, or Docker socket isolation guarantee. The initial beta is for **monitoring only**.
